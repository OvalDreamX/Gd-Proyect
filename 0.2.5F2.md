# 0.2.5C — Ship Asset Pipeline: runtime anchor integration (Phase 2C)
# -----------------------------------------------------------------------------
#
# Added:
# - Added `scripts/ship_anchor_integration.gd` and placed its node after the
#   visual mount but before camera/flight consumers in `scenes/ship.tscn`.
#   Why: imported Blender transforms must be available before the camera
#   controller caches its cockpit boresight and before any force consumer runs.
#
# - Applied `ANCHOR_pilot_seat` and `ANCHOR_cockpit_camera` to the existing
#   cockpit seat/camera nodes.
#   Why: player boarding and camera handoff keep using their established nodes;
#   only their ship-local transforms now come from the model when available.
#
# - Applied `ANCHOR_vane_*` locations to per-ship duplicated VaneDefinition
#   Resources, then rebuilt the controller's runtime lookup.
#   Why: Blender-authored force application points now control the physical
#   lever arms without mutating shared `.tres` resources or changing force
#   authority and flight tuning.
#
# - Added invisible direct-child Marker3D aliases for available
#   `ANCHOR_ground_probe_*` nodes.
#   Why: the existing ground-effect raycast system can consume Blender probe
#   positions through its established lookup path without a physics rewrite.
#
# - Migrated the prototype `ship.json` anchor references to canonical
#   lowercase IDs without the `ANCHOR_` prefix.
#   Why: JSON references and the code consuming them must change together;
#   this removes legacy mixed-case names and makes mapping exact.
#
# - Added an anchor-integration regression test using synthetic in-memory GLB
#   hierarchies, covering full and partial anchor sets.
#   Why: test transform mapping and fallback restoration before a finished
#   Blender asset exists.
#
# Fallback behavior:
# - A missing individual anchor does not reject a valid visible model.
# - Missing seat/camera anchors restore scene-authored transforms.
# - Missing vane anchors restore the original `.tres` local positions.
# - Missing ground probes return to the existing hull-derived fallback points.
# - Missing/invalid GLBs still retain the Phase 2B placeholder behavior.
#
# Scope preserved:
# - No collision shapes, rigid-body movement, mass, force authority, thermal
#   coefficients, flight-control behavior, environment scenes or project
#   settings were changed.

#   `docs/SHIP_ASSET_PIPELINE.md` before treating Phase 2C as runtime-verified.

# 0.2.5D — Ship Asset Pipeline: shared skeleton and action playback (Phase 2D)
# -----------------------------------------------------------------------------
#
# Added:
# - Added `scripts/ship_animation_controller.gd` to the mounted model group.
#   Why: the ship needs one stable API for discovering and requesting Blender-
#   authored mechanical actions without coupling the model asset to gameplay
#   code or running arbitrary scripts from a mod.
#
# - Added shared Skeleton3D validation: zero skeletons remains acceptable for
#   a static greybox, one non-empty skeleton is the supported rig, and multiple
#   skeletons or an empty skeleton disable action playback.
#   Why: all ship mechanisms should share one coherent skeleton while the
#   initial hull/anchor blockout can remain useful before rigging is finished.
#
# - Added discovery and validation for lowercase `action_*` AnimationPlayer
#   clips, including duplicate-name diagnostics.
#   Why: animation clips need predictable IDs that later gear, ramp and cockpit
#   systems can call without hardcoding Blender track paths.
#
# - Added `play_action`, `stop_action`, `stop_all_actions`,
#   `is_action_playing`, `get_available_actions` and `get_animation_status`,
#   plus `action_started` and one-shot `action_finished` signals.
#   Why: gameplay logic can trigger, inspect and stop a model-authored action
#   while the GLB remains data-only.
#
# - Runtime loop mode is applied to a duplicated Animation resource in the
#   generated AnimationLibrary.
#   Why: choosing one-shot or looping playback must not mutate the imported
#   source animation resource.
#
# Fixed:
# - Removed the direct `ShipAnchorIntegration` global-class type dependency
#   from `tests/ship_anchor_integration_test.gd`. The test preloads the script
#   and accesses its methods through `Node.call()`.
#   Why: standalone `--script` execution may compile before a newly added
#   `class_name` is present in Godot's global script-class cache.

# 0.2.5E — Ship Asset Pipeline: cockpit interaction discovery (Phase 2E)
# -----------------------------------------------------------------------------
#
# Added:
# - Added `scripts/ship_interaction_controller.gd` to the ship root. It
#   discovers `INTERACT_*` pivots under the mounted GLB, validates categories,
#   IDs and renderable descendants, and reports structured status.
#   Why: cockpit interaction identity should come from the Blender asset
#   hierarchy, not from duplicate coordinate tables or hardcoded mesh paths.
#
# - Generates a padded, minimum-size BoxShape3D hit area under each valid
#   interaction pivot, on a dedicated collision layer with overlap monitoring
#   disabled.
#   Why: cockpit ray tests need predictable selectable bounds without changing
#   the ship's rigid-body collision or normal physics contacts.
#
# - Added camera ray-picking, switch/button activation and normalized lever
#   value APIs plus interaction request/dispatched/failed signals.
#   Why: UI/input code can send explicit requests to the ship-owned controls
#   without letting a GLB asset choose arbitrary methods or scripts.
#
# - Added `scripts/ship_flight_controller_interaction.gd` as an inherited
#   extension of the existing FlightController script. A fixed allowlist maps
#   main power, field assist, throttle and vector angle controls to existing
#   flight/FCC state.
#   Why: expose a safe public boundary while preserving the existing flight
#   controller implementation and physics ownership.
#
# - Updated `scenes/ship.tscn` to use the inherited control bridge and attach
#   `InteractionController`.
#   Why: activate the Phase 2E asset pipeline on the prototype ship while
#   leaving mass, collision shape, flight forces and environment untouched.
#
# - Added synthetic discovery/hitbox/dispatch tests and an actual ship-scene
#   bridge test. Updated the asset pipeline docs and Blender cheatsheet.
#   Why: test both the data boundary and the connection to real existing
#   flight/FCC systems without requiring the finished Blender model.
#
# Limitations:

#   unbound because no landing-light gameplay subsystem exists yet.

# - This phase exposes ray-pick and lever-value APIs but does not hijack the
#   current flight mouse/keyboard input mode; input/UI decides when to call them.
# - Runtime verification against Godot 4.7.2 and the first real Blender GLB is

# 0.2.5.X — Actuator metadata foundation and cockpit bridge test correction
# -----------------------------------------------------------------------------
#
# Fixed:
# - Changed the cockpit bridge integration test to wait for the observed
#   STARTING -> ONLINE state transition, polling on physics frames with a
#   bounded timeout.
#   Why: the previous fixed 0.12-second timer had only a 0.02-second margin over
#   the controller's enforced 0.1-second minimum startup duration and could
#   expire before enough physics ticks had run. The production startup logic
#   and its minimum duration are unchanged.
#
# Added:
# - Added axis-family, local bidirectional thrust-axis and integer control
#   weights to VaneDefinition.
#   Why: separate Blender-authored actuator geometry from the control channels
#   that may recruit the actuator. One vane can contribute to lift and multiple
#   rotational axes without being assigned an exclusive maneuver role.
#
# - Updated ShipAnchorIntegration to build the runtime actuator list from
#   ship.json, reuse .tres definitions for fallback tuning, and register extra
#   JSON-declared actuators without a fixed seven-vane count.
#   Why: a ship's actuator inventory belongs to its data definition, not a
#   hard-coded prototype list. New actuators with missing anchors are retained
#   but disabled; existing actuators preserve their resource fallback position.
#
# - Migrated prototype vane anchors to the vertical, horizontal-side and
#   horizontal-main naming families and added pitch/roll/yaw/lift/main_thrust
#   control weights.
#   Why: the anchor prefix declares a bidirectional local thrust axis; JSON
#   weights describe which FCC demands may recruit that actuator.
#
# - Added integration-test coverage for axis metadata, control weights and an
#   eighth JSON-declared actuator. Updated the Blender cheatsheet and pipeline
#   documentation.
#
# Deliberately not included:
# - The existing fixed-group RepulsorliftSystem allocator remains active. The
#   new axis/weight metadata is prepared and registered but is not yet consumed
#   by the force allocator. The geometry-aware multi-axis allocator is the next
#   increment; do not claim changed flight behavior from this package.
# - Translation controls and Shift/Ctrl bindings are deferred until the FCC
#   exposes explicit translation demands and the input map can avoid existing
#   Shift-based interaction behavior.
#
# Verification status:
# - Source-level review and JSON parsing completed in the packaging environment.
# - Godot 4.7.2 runtime tests were not executable in this environment; the
#   project owner must run the listed regression tests after applying the patch.

# 0.2.5F.2 — Actuator regression-test corrections
# -----------------------------------------------------------------------------
#
# Fixed:
# - Removed the call to `duplicate(true)` on `ShipDefinition` in
#   `tests/ship_anchor_integration_test.gd`.
#   Why: ShipDefinition is a RefCounted data object, not a Resource, so it does
#   not provide Resource.duplicate(). The test now deep-copies only the mutable
#   vane-definition array, temporarily assigns the extra test actuator, and
#   restores the original array before continuing.
#
# - Corrected the operating-temperature setup in
#   `tests/vane_force_model_test.gd`.
#   Why: new vane runtime states begin at -10 C, where the existing cold-strain
#   model intentionally limits output to 70%. The old test compared this
#   cold-start output (415453.5 N) against the 100%-warm rated result
#   (593505 N), despite never warming the test vanes.
#
# - Added an explicit 70% cold-start force assertion, a 60 C nominal-temperature
#   setup for the rated 1.1 TWR assertion, and a check that `reset_all_vanes()`
#   restores the -10 C default before the test re-establishes its warm baseline.
#   Why: force-model tests must control thermal initial conditions rather than
#   weakening or bypassing the production cold-authority behavior.
#
# Scope preserved:
# - No production scripts, force calculations, thermal rules, actuator metadata,
#   JSON configuration, scenes, environment content or input bindings changed.
# - The fixed-group allocator remains active; geometry-aware allocation is

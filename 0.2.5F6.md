# Space Trucker 0.2.5F6 — Geometry-driven yaw allocation

## Baseline

Implemented against branch `0.2glb-integration`, commit `539eb8a2b3223d517e3d7dba9c2861b0a6e731bd` (F5.7 state). This phase completes the previously deferred yaw path only. Main propulsion/vectoring remains on the established path; translation controls remain unbound.

## Root cause and geometric correction

The previous prototype yaw actuators were placed at opposite X offsets but declared `horizontal_side`, which maps to a local-X thrust axis. For points separated along X, an X-directed force is collinear with that separation and cannot create the required moment around local Y. The old `_apply_yaw_pair()` concealed this mismatch by bypassing the actuator axis metadata and directly assigning longitudinal `-Z/+Z` force directions.

F6 makes the model convention and physics agree:

- Port yaw actuator anchor: `ANCHOR_vane_horizontal_main_side_left`.
- Starboard yaw actuator anchor: `ANCHOR_vane_horizontal_main_side_right`.
- Both declare the `horizontal_main` family, whose bidirectional local axis is `+Z`.
- Their Empty positions remain separated along local X and continue to define their actual force application points.

Positive yaw retains the established sign: port pushes forward (`-Z`), starboard pushes aft (`+Z`), their net translation cancels, and the resulting torque is around local `-Y` (nose right). The `horizontal_side` family remains local `+X` for actuators whose actual thrust axis is lateral; it is no longer used for this yaw pair.

See `docs/VANE_YAW_GEOMETRY_F6.md` for the model-authoring contract and the explicit migration table. That addendum supersedes older prototype examples that named these two yaw anchors `ANCHOR_vane_horizontal_side_a/b`.

## Runtime changes

### `scripts/repulsorlift_system.gd`

- Added yaw to the active channel set in `_apply_maneuver_allocator()`.
- Added geometry-derived yaw torque capacity using each eligible actuator's effective axis, force limit, and COM lever arm.
- Added a normalized yaw torque demand using the existing allocator convention: positive FCC yaw requests negative local-Y torque.
- Pitch, roll and yaw now share one allocator invocation and one bounded scalar output per actuator. Shared actuators therefore cannot be assigned one independent pitch output and a second independent yaw output during the same force update.
- Removed the hard-coded left/right yaw-group force path and its group-specific helper methods/constants from this system.
- Preserved per-actuator application points, alignment drift, thermal/damage authority, torque telemetry, force debug vectors, and thermal load contributions.
- Made damage redistribution channel-aware: a damaged yaw actuator can draw recovery headroom only from healthy yaw-capable actuators, rather than borrowing unrelated bottom-vane pitch/roll headroom. A physical actuator that supports several active channels still has one shared extra-authority cap, so its combined redistributed authority cannot exceed its own configured output headroom.
- Preserved the prototype's previous full-command yaw authority. The existing `maneuver_authority_fraction` remains a pitch/roll feel scalar and is deliberately not applied to yaw.
- Kept the main-vector implementation and its main/lift groups unchanged for F7.

Debug vectors for side actuators that contribute only yaw remain tagged `yaw`, including during simultaneous pitch/roll/yaw commands. A future actuator with active weights on yaw and another simultaneously commanded channel is tagged `maneuver`, because its single output is the joint solution.

### Data and authoring

- Updated `data/vanes/side_left.tres` and `side_right.tres` to use `axis_family = horizontal_main` and `local_thrust_axis = +Z` as the no-model fallback.
- Updated the prototype JSON side-vane anchor references to the two new `horizontal_main_side_*` anchors. Stable vane IDs, group strings, 0.03 TWR ratings, and yaw weights remain unchanged.
- The legacy `control_sets.yaw_left/yaw_right` metadata and `group` identifiers remain in JSON because the current schema still accepts/requires the group field and other legacy paths have not yet been retired. They are not consulted by the new yaw allocator.
- Updated `tests/ship_anchor_integration_test.gd` synthetic model anchors and added assertions that name-based integration resolves the side-mounted yaw pair to local +Z while preserving their port/starboard lever arms.
- Added `tests/vane_yaw_geometry_test.gd` for pure geometric impossibility, actual runtime yaw direction/force cancellation, arbitrary shared group IDs, combined pitch/roll/yaw allocation bounds, and channel-specific damage redistribution.

## Design constraints preserved

1. Anchor name family declares the available bidirectional thrust axis; anchor position declares the application point. Anchor rotation is not consumed for thrust direction.
2. Control weights describe recruitment, not exclusive actuator roles or literal force percentages.
3. One actuator has one scalar output per solve. All simultaneously active rotational axes must be solved together.
4. Force is applied at the actuator's physical application point relative to the ship origin; the allocator's wrench is calculated about the current COM.
5. No thermal simulation, damage-state/authority curve, mass, COM, FCC input, main-vector, environment or project-setting behavior was changed. The one related behavior refinement is channel-aware routing of the existing damage-redistribution budget, so recovery headroom is not borrowed from actuators that cannot provide the damaged channel's moment.
